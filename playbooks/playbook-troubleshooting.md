# Runbook: отладка детекта в Wazuh («событие есть, а алерта нет»)

**Назначение:** методика поиска, где теряется событие, когда атака произошла, но правило корреляции не сработало.
**Платформа:** Wazuh 4.9.2, Windows-агенты (eventchannel)
**Автор:** Богданов А.В. · Выведено из отладки правила 101000 (DCSync) на стенде

---

## 1. Принцип

Путь события от хоста до алерта — это цепочка звеньев. Алерта нет = событие потеряно на одном из них. Диагностика идёт **звено за звеном от источника**, а не гаданием по правилу.

```
[1] Аудит        → событие вообще пишется в журнал?
      │
[2] Генерация    → событие есть в локальном журнале Security хоста?
      │
[3] Доставка     → событие дошло до менеджера Wazuh?
      │
[4] Декодер      → каким декодером распарсилось, какие поля?
      │
[5] Правило      → матчится ли (if_sid, поля, опечатки)?
      │
[6] Индексация   → алерт попал в индекс / видно в Discover?
```

На каждом звене — своя проверка и свои типичные причины.

---

## 2. Звено 1 — Аудит (пишется ли событие)

Многие события (4662, 4688, доступ к объектам) логируются только при включённой субкатегории аудита, иногда + SACL на объекте.

```
auditpol /get /subcategory:"Directory Service Access"
auditpol /get /category:*          (полный обзор политики аудита)
```

**Типичные причины:**
- субкатегория = «Нет аудита» → включить: `auditpol /set /subcategory:"..." /success:enable`;
- нет SACL на объекте (для 4662 — на разделе домена) → добавить через ADSIEdit/dsacls.

---

## 3. Звено 2 — Генерация (есть ли событие локально)

Проверяем прямо в журнале хоста, минуя Wazuh:

```
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=<EventID>; StartTime=(Get-Date).AddMinutes(-30)} -MaxEvents 20 |
  Format-List TimeCreated, Message
```

- **События есть** → генерация ОК, идём к звену 3;
- **Событий нет** → проблема в аудите (звено 1) или событие просто не возникает при этой активности.

---

## 4. Звено 3 — Доставка (дошло ли до менеджера)

Два способа.

**(а) Конфиг агента** — не отфильтровано ли событие в `ossec.conf`:
```
Select-String -Path "C:\Program Files (x86)\ossec-agent\ossec.conf" -Pattern "Security|query|<EventID>" -Context 2,2
```
Смотреть блок `<localfile><location>Security</location>` и его `<query>` — не стоит ли `EventID != <наш>`.

**(б) Полное логирование на менеджере** (самый надёжный факт приёма). В `ossec.conf` менеджера:
```
<global>
  <logall>yes</logall>
  <logall_json>yes</logall_json>
</global>
```
Рестарт → повторить активность → искать событие среди ВСЕХ принятых:
```
sudo grep -c '"eventID":"<EventID>"' /var/ossec/logs/archives/archives.json
sudo grep '"eventID":"<EventID>"' /var/ossec/logs/archives/archives.json | head -1
```

- **count > 0** → событие доходит; проблема в декодере/правиле (звено 4-5). В найденной строке сразу смотреть `decoder.name` и поля;
- **count = 0** → не доходит; причина в агенте (фильтр `<query>`, канал не собирается, служба агента).

> **ВАЖНО:** `wazuh-alerts-*` (Discover) содержит **только сработавшие правила**. Сырое событие без матча правила туда НЕ попадает. Поэтому «пусто в Discover» ≠ «событие не пришло» — проверять надо через archives.
> **НЕ забыть** вернуть `logall` в `no` после отладки — архив быстро ест диск.

---

## 5. Звено 4 — Декодер (как распарсилось)

Из строки archives берём `decoder.name` и имена полей. Это критично для правила.

- событие Windows eventchannel в бою декодируется **`windows_eventchannel`**;
- проверить, что поле, на которое завязано правило, реально распарсилось и названо так, как в правиле (`win.eventdata.properties`, `win.system.eventID` и т.д.).

> **Ловушка logtest:** при подаче сырого JSON вручную в `wazuh-logtest` срабатывает общий декодер **`json`**, а не `windows_eventchannel`. Поэтому logtest плохо тестирует `decoded_as windows_eventchannel`-правила — ориентироваться на реальный `decoder.name` из archives.

---

## 6. Звено 5 — Правило (матчится ли)

Три частые причины, что правило не срабатывает:

**(а) Опечатка в имени поля.** PCRE2 по несуществующему полю всегда ложно, молча.
Пример: `propetries` вместо `properties` → правило не матчит никогда.

**(б) Неверный `if_sid` (родитель).** Реальный родитель может отличаться от предполагаемого по описанию. Найти под какое базовое правило падает событие:
```
sudo grep -rn "<EventID>" /var/ossec/ruleset/rules/
sudo grep -nE 'rule id="(60100|60103|60104)"' /var/ossec/ruleset/rules/0580-win-security_rules.xml
```
Для Windows Security: **60100** (все security), **60103** (AUDIT_SUCCESS), **60104** (AUDIT_FAILURE).

**(в) `decoded_as` вместо `if_sid`.** На практике кастомные правила на windows_eventchannel надёжнее якорить через **`if_sid` базового правила**, а не `decoded_as`. Рабочие правила курса (100200 `if_sid 61612`, 100600 `if_sid 92652`) это подтверждают.

**Приём «ловушка»:** временно добавить минимальное правило на любое событие этого типа — если оно загорается, базовый матчинг работает, и дело в условиях боевого правила:
```xml
<rule id="100111" level="5">
  <if_sid>60103</if_sid>
  <field name="win.system.eventID">^4662$</field>
  <description>TEST: ловушка</description>
</rule>
```

**Всегда проверять синтаксис перед рестартом:**
```
sudo /var/ossec/bin/wazuh-analysisd -t
```
Если ruleset не компилируется — Wazuh молча работает на последней валидной версии (и правка «не применяется»).

---

## 7. Звено 6 — Индексация (видно ли в Discover)

Если на уровне менеджера алерт есть, а в дашборде нет:
```
sudo grep '"id":"<rule.id>"' /var/ossec/logs/alerts/alerts.json | tail
```
- в `alerts.json` **есть**, в Discover **нет** → проблема индексации/времени (неверный time range, индекс-паттерн, лаг индексатора);
- в `alerts.json` **нет** → правило не сработало, вернуться к звену 5.

---

## 8. Чек-лист быстрого прохода

- [ ] `auditpol` — субкатегория включена (+ SACL для доступа к объектам)
- [ ] `Get-WinEvent` — событие есть в локальном журнале хоста
- [ ] `ossec.conf` агента — событие не отфильтровано в `<query>`
- [ ] `archives.json` (`logall`) — событие дошло до менеджера (+ смотрим `decoder.name` и поля)
- [ ] имена полей в правиле = реальные (нет опечаток)
- [ ] `if_sid` = реальный родитель (60103 для AUDIT_SUCCESS); не `decoded_as`
- [ ] `wazuh-analysisd -t` — ruleset компилируется
- [ ] ловушка на EventID загорается → базовый матчинг ОК
- [ ] `alerts.json` на менеджере / Discover — алерт виден
- [ ] вернуть `logall` в `no`, убрать ловушку

## 9. Реальный кейс (DCSync, правило 101000)

Симптом: атака выполнена (secretsdump), 4662 **нет** в Discover.

Диагностика по звеньям:
1. Аудит — Directory Service Access = Success ✓
2. Генерация — 4662 есть в локальном журнале ✓
3. Доставка — `archives.json`: count=33, `decoder.name: windows_eventchannel` ✓ (дошло, значит дело в правиле)
4. Декодер — поля распарсились, `properties` содержит GUID ✓
5. Правило — **две ошибки:** опечатка `propetries`→`properties` + неверный якорь `decoded_as` → заменён на `if_sid 60103`
6. После правки — 101000 загорелось (level 14) ✓

**Вывод:** проблема была не в доставке (как казалось), а в правиле — но доказать это можно было только пройдя всю цепочку до archives. Гадать по правилу с самого начала = потеря времени.
